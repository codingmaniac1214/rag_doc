Introduction 1.1 General The Stream Server (StrSvr) is a generic infrastructure component which can be used to provide streams of data over OpenAccess conforming to either the Reliable DataStream (RDS) or Transaction protocol. When providing an RDS feed, StrSvr acts as a server, accepting incoming connections from a client and supplying data depending on requests sent by that client. When providing a transaction stream, StrSvr connects to a transaction server and sends in transactions as defined by the configuration. Both streams can be recovered or resumed in the manner defined by the OpenAccess Programmer’s Guide. The following summarises the key features of each stream as implemented by StrSvr. 1.2 RDS • A resumable stream of data, generated by scanning a configured combination of relationally joined tables. • Provided in batches. • Translation of database data in SDS format can be done either through configuration or through bespoke code, linked against the stream server library (libFIDStrNode). • Real-time updates supported • Optionally, user access can be restricted on a per-datastream basis. The following diagram shows a possible context for StrSvr when providing an RDS stream. Here, StrSvr is forming the interface between the Fidessa Trading System, and a customer back office application. The stream is resumed at the point at which it was curtailed by requesting the last processed source reference from the server. Configuration Notes This section takes you through the items which can be used to modify the behaviour of StrSvr through configuration. 2.1 general Block The outer block of the configuration file should be called StrSvr. Inside here, the first thing that should appear is a block called general - the top of an example configuration might look like this: StrSvr { general { processName STRSVR streamServiceName FTS_RDS } The general block contains two items, both of which are optional. These are described in the following table. Name Default Description processName STRSVR Defines the name used when the process logs a message in the system-wide operator log. You should make this name unique within your system. streamServiceNa me STREAM Name of the OpenAccess service which this application will provide. When the application starts, the OpenAccess library will check in the OAServices file for this name, and if it is present, it will declare itself on the specified port. Clients will then be able to connect to this service to request your RDS streams. Note that the general block can be omitted, and if it is, the items within it will take the default values mentioned above. 2.2 expression Block Following the general block, the standard expression block may optionally be present: Page 10 Configuration Notes Fidessa Product Infrastructure © 2025 Fidessa plc Issue: 1.2 Version 8.0 Status: Released OpenAccess Stream Server Configuration Guide File: FPI_STR_CNG expression { dll ( "libIDSFTS.so" ) xrefTables { Roman { I One II Two III Three IV Four V Five } } preExpression ( "Display('Evaluating StrSvr pre-expressions\n')" ) } The expression block allows you to configure attributes of the expression evaluator, including the following: • dynamically linked expression libraries (libraries provided by royalblue which provide business-specific expression functions) • cross-reference tables (which install cross-referencing functions for use in subsequent expressions) • pre-expressions (a list of expressions which are evaluated once, at start-up) For full details, see the Fidessa Expression Evaluator Programmer’s Guide. 2.3 linkMgr Block After this block, the OpenAccess library is configured, using the linkMgr block. For more details concerning this block refer to the Expression Evaluator Programmer’s Guide. 2.4 streamNode Block Following this general configuration is the streamNode block, which defines the configuration of each stream. Logically, references are built from database key values (as these are unique to each record) as the concatenation of the string conversions of the fields in a key. The fields are delimited by the delimiter character, so that when recovering a stream, StrSvr can quickly reconstruct the key value corresponding to a reference. Hence the delimiter character should be guaranteed not to appear in your string data. By default, StrSvr uses the pipe character (|), but if this is used in your string data, you will need to use an alternative. Note: The pipe character was chosen because it rarely appears in string data. You are strongly advised to use this default. This key should be sorted (so that StrSvr can scan down it in order), and it should either increase or decrease monotonically with time, i.e. every update which comes in should have a key value which is always either greater or less than the previous update. For example, a timestamp key satisfies this criterion (as the timestamp always increases), but a key on an internal trade identifier may not increase monotonically, as old trades may be amended. A key may be used which is monotone decreasing as well as increasing. To use a decreasing key, set reverseSort to YES. 2.5.2 Update Regime Versions of StrSvr prior to v6.0.0 had a complex regime for polling for updates, which involved matching new data with updates in order to guarantee only sending data which had been correctly journalled. If, for any reason, data could not be matched with updates, StrSvr would produce the following operator message: Configuration Notes Page 21 Issue: 1.2 © 2025 Fidessa plc Fidessa Product Infrastructure Status: Released Version 8.0 File: FPI_STR_CNG 30 JUN 1998,10:48:06,WAR,INF_STRSVR-0-Reliable stream lagging behind - check log file Note that in v6.0.0 and later infrastructure releases, the update regime has been changed such that this can no longer occur. 2.5.3 Flow Control and Timeslicing Rows are sent to clients in batches, to enable flow control. If the client does not specify a batch size when logging on, a default will be used. You can specify the default number of rows in a batch with the defaultMaxCount item. In order to service multiple clients at once, StrSvr timeslices scans. A certain number of rows are scanned on behalf of each client before moving on to service a different request. You specify a number of rows to scan in the rowsPerTimeslice item. 2.5.4 Translating Records into Datastream Messages The XLator item defines how rows are translated into messages for transmission to the client. It can take the value DEFAULT, in which case the default translation is used: this turns a database record into a SDS buffer with the same name as the record, and with the fields named within that SDS buffer, with a type appropriate to their database type. This default translation can be enhanced through expressions - see below for more details. The XLator item can also take the value NONE, in which case no translation is applied, and the datastream message must be set up purely in configuration. The following sections show how to do this. The XLator item can also take the value embed. This will embed in the returned SDS a repeating SDS of the records that are specified in the Embed block. For example, user data is specified in the rdsTemplate and the groups to which the user belongs could be returned in the repeating SDS array. - see Appendix A: The EMBED XLator for more information. If the stream node library has been linked into another application and extra translators added, these can be named here. For example, the TrdStr process in FTS defines a specialised translator called TRADE which translates records from the FTS trade tables into the documented external representation. If the default translator is in use, the following can also appear in your rdsTemplate block: Page 22 Configuration Notes Fidessa Product Infrastructure © 2025 Fidessa plc Issue: 1.2 Version 8.0 Status: Released OpenAccess Stream Server Configuration Guide File: FPI_STR_CNG defaultXLator { omitFields ( "NULL_MAP", "TIMESTAMP" ) } This block specifies a list of fields in each record which the default translator will omit from its translation. Combined with the fieldExprs list (see below) this allows you to customise the default translation to your own requirements. 2.5.5 Enhancing Translation with Expressions The fieldExprs item (which follows the table blocks described below) is a list of expressions which are evaluated after the translator has been applied. They are evaluated in the context of the scanned database row, so aliases of records in this row can be used to refer to particular fields. You can also write fields into the message to be sent with these expressions. Any item with no alias is assumed to refer to the outgoing message, and as with all SDS expressions, you should specify the type with which to address the data. For example, the following configuration might be used in the FTS TrdStr process to add a supplementary field to the hard-coded conversion: rdsTemplate { ! Standard configuration, etc etc ! Use hard-coded trade model translator XLator TRADE ! Add an additional field fieldExprs ( “TRADE.CUSTOM.DATABASE_TIMESTAMP.s = TIMESTAMP.FULL” ) } Note: See the Fidessa Expression Evaluator Programmer’s Guide for full details of SDS and database record expressions, and for available expression functions and operators. 2.5.6 Configuring the Tables to Scan The table blocks configure the tables to be scanned and the relational joins between them. Within these blocks, you can define: • Filters for individual tables which are expression based. • Aliases for individual records, allowing them to be uniquely referenced in subsequent expressions. The exact configuration is described in the Fidessa Expression Evaluator Programmer’s Guide. In addition to the standard configuration, there are two embedded variables maintained by StrSvr, for use in your where expressions. These are joinOk, which is non-zero if Configuration Notes Page 23 Issue: 1.2 © 2025 Fidessa plc Fidessa Product Infrastructure Status: Released Version 8.0 File: FPI_STR_CNG the join to the current record succeeded (i.e. at least one corresponding record was found) and isUpdate, which is non-zero if the current row was generated from an update to the database (as opposed to being recovered as part of an initial scan). joinOk is clearly only available in non-primary records, but isUpdate is available in all where expressions. The following example shows the use of joinOk and isUpdate to filter a scan. table { name TRADE_SUMMARY alias ts } table { name ALT_INSTRUMENT_ID join “ai.INSTRUMENT_ID = ts.INSTRUMENT_ID; ai.ALTERNATE_TYPE = ‘RIC’” ! Only return a row when the underlying instrument has a RIC code, ! and only do so for an update where “joinOk && isUpdate” } 2.5.7 Parameterised logon The where expression is introduced in order to allow for the post-filter parameterisation from reliable datastream clients. In addition to the standard aliases a new logon alias can also be used. This provides access to the complete message sent by client on logon. The following example makes the stream server stream out only the rows time-stamped with the same date as the one of the logon datastream reference: where "Mid$(logon.DATASTREAM_REF.s,0,8) == Mid$(t.TIMESTAMP,0,8)" 2.5.8 Extra events There is an option of enabling multiple events to be generated from a single database row by specifying them in the extraEvent blocks. For example, if only an amend is stored in the RTD, but a separate cancel and rebook are required on the stream. Extra events are fired after the default, normally sent, message, and each of them has its own filter, translator and field expressions. These are configured in the same fashion as for the main event. In order to guarantee recoverability the design of the event matching datastream reference has changed slightly. It now includes an extra delimiter and a sequence number that identifies event in a sequence for matching database row. Sequence number starts from 0 and increases for successive events accordingly. This behaviour can be modified by setting maxOutstanding to an integer greater than 1. If this is done, a number of transactions are allowed to be outstanding with the Configuration Notes Page 33 Issue: 1.2 © 2025 Fidessa plc Fidessa Product Infrastructure Status: Released Version 8.0 File: FPI_STR_CNG transaction server before waiting for any responses, so, if 5 is configured in this item, StrSvr will generate 5 transactions and send them to the transaction service before waiting for the replies. When the first reply is received, another transaction will be generated, ensuring that this number of transactions are always outstanding. Additionally, on start-up, if StrSvr recovers the position in the transaction stream, it will also recover the statuses of this number of preceding transactions. For example, if maxOutstanding is set to 5, and StrSvr starts up and finds that the tenth transaction in a stream was the last one to be processed, it will recover the statuses of the tenth, ninth, eighth, seventh and sixth transactions in the stream. Note: Asynchronous behaviour, using large outstanding counts, can result in greatly increased performance. 2.7.3 Synchronisation To avoid time consuming RTD forward scans in case of rarely used streams, transaction and result streams are synced up. The synchronisation is according to the latest record in the real time database, just after its activity has quiesced. In order to enforce this, an expiry of the idle period, set by preSyncIdlePeriod configuration item, triggers the synchronisation messages to the corresponding transaction sinks. Note: Normally, this item is not specified. 2.7.4 Result Events The next block of interest is the resultEvents block. This can be used to force a failover between broadcast systems, for example, when a link to an external data provider fails. Configuration Notes Page 37 Issue: 1.2 © 2025 Fidessa plc Fidessa Product Infrastructure Status: Released Version 8.0 File: FPI_STR_CNG When data is deemed to be fresh, StrSvr’s OpenAccess service is up, and reliable datastreams can be requested by client applications. Additionally, transaction streams are active. When data is deemed to be stale, StrSvr’s OpenAccess service is down, and hence reliable datastreams are not available. Also, transaction streams are stopped. The dataFreshWhere block is configured as follows: dataFreshWhere { table SESSION_STATUS dataFreshWhere "SERVICE_CODE=='BDG044' && SESSION_STATUS=='U'" dataStaleWhere "SERVICE_CODE=='BDG044' && SESSION_STATUS=='D'" } When the DATABASE_AVAILABLE state is received, the configured table is scanned, and the dataFreshWhere expression is evaluated for each record. The data is deemed to be fresh if the expression evaluates to a non-zero value for any record. After the initial scan, StrSvr listens for updates to the specified table, and does the following: • If the data is currently fresh, the dataStaleWhere expression is evaluated for each update. If the expression evaluates to a non-zero value, the data is deemed to be stale. • If the data is currently stale, the dataFreshWhere expression is evaluated for each update. If the expression evaluates to a non-zero value, the data is deemed to be fresh. This arrangement of expressions allows for cases where the data fresh and data stale conditions are not mutually exclusive; e.g. in the example, the SESSION_STATUS flag is tri-state. The following table summarises the configuration options for the dataFreshWhere block. Name Default Description table None (Mandatory) Defines the table to scan. This can also be configured to hold table blocks as used by the database scanner. dataFreshWhere None (Mandatory) Expression which should return an integer value. Data is initially fresh if a non-zero value is returned for any record in the configured table. If data is stale, it becomes fresh when an update occurs for which this expression evaluates to a non-zero value. Appendix C: Pitfalls 7.1 Global Variable Use Sometimes, global variables are set in database scanner expressions to avoid repeating configuration in the field expressions. There are some issues regarding global variable use that require a special treatment. table { name ORDER where “globalVar##s=FIELD1; 1” } fieldExprs(“FIELD2.s=globalVar##s”) Under heavy system load the value of the global variable set in the database scanner configuration can change before the field expressions get evaluated. Thus we end up using an overwritten value of globalVar. In order to get round this a new technique was introduced. It uses a global property- value map where one can store, retrieve, and delete named property values using the appropriate expression evaluator functions (MapAdd, MapGet, and MapDelete). The problem is solved by using some of the key field values to form a unique property name that will be stored in the global map along with its value. Previous example rewritten using global map functions: table { name ORDER where “MapAdd(‘globalVar’+ ORDER_ID, FIELD1)” } fieldExprs(“FIELD2.s=MapGet(‘globalVar’+ ORDER_ID)”) Values are now safely stored in the global map and they can be retrieved later. 7.2 Backward Joins There is no support for backward joins within the stream server. In software versions prior to v6.1.3, they cause no errors but are silently ignored. From v6.1.3 onwards, the stream server validates that no backwardJoins are present in the configuration. New in v6.1.3 Page 52 Appendix C: Pitfalls Fidessa Product Infrastructure © 2025 Fidessa plc Issue: 1.2 Version 8.0 Status: Released OpenAccess Stream Server Configuration Guide File: FPI_STR_CNG 7.3 Update Accumulation After the initial scan has finished, the stream server may react to updates on relevant rows, configured up within database scanner blocks. That happens if their key changes in a way that it becomes “top of the list” and then an appropriate message is built and sent off against the configured stream. Thus many updates to a single row are published on a stream. When performing a recovery on a stream, the stream server is only able to recover the last message on the stream originating from an update to a particular row. This means that the history information concerning consecutive updates on a row is not recovered and should not be expected. Inserted rows are fully recovered with the presumption they have not been deleted since they were last streamed out. 7.4 Stream Resumption v6.x.x stream servers will refuse to resume a transaction stream for which there is no last SOURCE_REF. This is a safety feature, designed to avoid the accidental replay of entire streams, but it can make it difficult to roll out new streams. From v6.1.13, StrSvr supports an expression which can be specified in configuration, which allows an initial SOURCE_REF to be defaulted when none is present. This allows StrSvr to resume a stream from a safe point. As most streams are keyed using database timestamps, a sensible resumption point is the current time; this ensures that historic data is never accidentally re-sent. Appendix D: The SOURCE_KEY field If two stream servers were to use the same SOURCE_ID for sending transactions to the same transaction sink, recovery problems would ensue. From v6.1.3 onwards, a degree of protection has been added to the stream server, such that only one process can use a particular SOURCE_ID. This is implemented using the new SOURCE_KEY field, which is sent on every transaction. This field contains enough information to uniquely identify the sending process - primary and standby hostnames, runtime account name, and process name. When the stream server initially synchronises, the transaction sink records the SOURCE_KEY value; all subsequent transactions from the same SOURCE_ID must specify the same SOURCE_KEY. Thus if another process uses the same SOURCE_ID, the transactions would be rejected, avoiding recovery problems1. This of course relies on the SOURCE_KEY being supported by the target transaction sink; this support has been added in v6.1.3. SOURCE_KEY values are stored in the SOURCE table. 8.1 Backward Compatibility Because SOURCE_KEY is an additional, header-level field in each transaction, it could result in NACKs from existing transaction handlers. Compatibility issues are handled as follows: 8.1.1 Post-v6.1.3 StrSvr, pre-v6.1.3 transaction processor This case is handled automatically. During the initial recovery sequence, the stream server spots that the transaction processor does not support the new field, and does not send it on subsequent transactions.
